Your GPT-4o Is Retiring. A Model Swap Is Not an Upgrade Until You Have Tested It

If you run anything on Azure OpenAI, you probably received the same email we did this week: "Retirement notice: Azure OpenAI GPT-4o, GPT-4o-mini, and GPT-4.1-mini model version(s) … will be retired". Date: 14 April 2027. Tracking ID in Service Health: MR5M-CG0.

It is tempting to file it under "later". Five months feels like plenty, the email talks about automatic upgrades, and the replacement models are newer, so surely they are better. That reasoning is about half right, and the wrong half is the expensive one.

This post is meant as coaching rather than an alarm bell. What does the swap actually change for quality, for token consumption and for your bill? And what does it tell you about how to run AI workloads from now on?

What the notice actually says

On 14 April 2027 the following versions stop working in Azure public cloud:

  • GPT-4o, versions 2024-08-06 and 2024-11-20
  • GPT-4o-mini, version 2024-07-18
  • GPT-4.1-mini, version 2025-04-14

The notice names a replacement per deployment type. For Global and Data Zone deployments, all four are replaced by gpt-6-luna (2026-09-22). For regional deployments, GPT-4o maps to gpt-5.1 (2025-11-13) and the two mini models map to gpt-5-mini (2025-08-07).

Read that table twice. A small, cheap, non-reasoning model such as GPT-4o-mini is being replaced by a member of the GPT-6 reasoning family. That is not a patch release. It is a different kind of engine under the same bonnet.

Two other sentences in the notice deserve more attention than they get. First: "Provisioned deployment types must be manually migrated by the customer." Second: "Replacement-model pricing may differ based on the model and deployment type." Microsoft is being polite. Translated: if you run PTUs, nothing happens for you automatically, and if you run pay-as-you-go, something happens whether you are ready or not.

The model retirement schedule on Microsoft Learn confirms the date. At the time of writing it still lists gpt-5.1 as the replacement for GPT-4o and no replacement for the minis, so expect the page to catch up with the notice. The notice itself warns that retirements can take up to two weeks to appear everywhere.

What happens if you do nothing

Every Standard, Global Standard and Data Zone Standard deployment has a version upgrade policy, the versionUpgradeOption. Microsoft documents three values in Working with models:

OnceNewDefaultVersionAvailable moves the deployment to a new default version within two weeks of that default changing. OnceCurrentVersionExpired moves it to the current default when the retirement date arrives. NoAutoUpgrade does nothing, and the deployment simply stops working on retirement day.

Here is the detail that catches people out: if you never touched this setting, the value is null, and null behaves like OnceCurrentVersionExpired. So the most common situation in the field is this: on 14 April 2027 your application keeps answering, but a different model is doing the answering. No deploy, no change ticket, no test run.

Microsoft says it plainly in its own model migration guidance: "An endpoint that still responds doesn't mean your app still behaves correctly." Auto-upgrade is a safety net. It is not a migration plan.

Provisioned deployments have no safety net at all. They are not auto-upgraded, and retirement dates are not extendable. If you run PTUs, make sure you also have quota for the target model before you need it.

Quality: different, not automatically better

A newer model will usually score higher on a public benchmark. Your application is not a public benchmark. It is a specific prompt, a specific tone of voice, a specific JSON shape that some downstream code parses, and a specific set of tools the model is expected to call in a specific order.

When you move from GPT-4o or a mini model to a reasoning model, these are the things that typically shift:

  • Verbosity. Answers get longer, or sometimes noticeably shorter.
  • Formatting and structured output. A schema the old model followed loosely may now be followed strictly, or differently.
  • Tool calling. Argument names, ordering and the number of calls can change.
  • Refusal behaviour and tone.
  • Latency, and especially the variance in latency.

Parameters are a quiet source of breakage too. The reasoning models documentation explains that reasoning models use max_completion_tokens in Chat Completions and max_output_tokens in the Responses API, and that defaults for reasoning_effort differ by model. gpt-5.1, for example, defaults to no reasoning at all unless you ask for it. Code that was written for GPT-4o can run without errors on the new model and still behave quite differently.

My advice: do not judge the new model by asking it five questions in the playground and thinking "that looks fine". Judge it on your own traffic.

Tokens: the line item that will surprise you

This is where the move to a reasoning model matters most, and where the email says the least.

Reasoning models think before they answer. That thinking is made of reasoning tokens: you never see them in the response, but Microsoft is explicit that they are billed as output tokens. A short, crisp answer can therefore still cost a lot, because the model may have spent thousands of tokens getting there. And output tokens are usually the expensive ones.

Three practical consequences.

Your token cap now covers thinking as well as answering. max_completion_tokens and max_output_tokens limit reasoning plus visible output together. Set the cap too low and the response comes back with status: "incomplete", possibly before a single visible word. You pay for the input and the reasoning and you get nothing back. Microsoft suggests reserving at least 25,000 tokens while you learn how a workload behaves. Check status on every response, not just whether the content is empty.

reasoning_effort is now a cost dial. Values run from none through low, medium and high to xhigh and max, depending on the model. A classification or routing task that ran happily on GPT-4o-mini rarely needs high. Start low, measure, and only turn it up when your evaluation shows a gain worth paying for.

The bigger context window is a temptation, not a recommendation. The GPT-6 family offers a context window of over a million tokens. That is useful for genuinely long documents. It is also an invitation to stop curating what you send, and every resent conversation turn is paid input. Look at prompt caching before you look at bigger prompts.

Caching itself changes too. On GPT-4o, writing to the prompt cache was free and reads were discounted. From the GPT-5.6 family onwards, which includes gpt-6-luna, cache writes can be charged on top of discounted reads. The advice is the same, but the stakes are higher: keep the reusable part of your prompt identical and at the front, so you pay for reads rather than repeated writes.

Microsoft's own migration guide puts a number on it: reasoning tokens, cached input and structured-output overhead can swing unit economics by 2x or more. So do not compare list prices per million tokens. Replay a week of real traffic, count the tokens, and project the monthly bill from that. List prices for each model are on the Azure OpenAI pricing page.

The honest summary: the new model may well do more for every token it spends. It is also likely to spend tokens in places you did not budget for. Both can be true at the same time.

Five questions to put to your team this month

Coaching is mostly asking the right questions, so here are the ones I would put on the table.

  1. Which deployments do we have, on which model version, which deployment type, and which upgrade policy?
  2. Who owns each of them? Not the subscription, the actual workload.
  3. Do we have a frozen test set of real inputs with expected outputs, so we can compare old and new on equal terms?
  4. What does a month of our actual traffic cost on the new model, including reasoning tokens?
  5. Where do we keep the old deployment running, and for how long, so that rollback is a decision rather than a scramble?

If the honest answer to question three is "no", that is your real task. Everything else is easy once that exists.

A sensible plan for the next five months

Microsoft's migration process has six phases: discover, assess, adapt, validate, roll out and retire. Translated to a calendar it looks something like this.

November and December: inventory and capture. List every deployment, its version and its versionUpgradeOption. Start logging prompts, responses, latency and token counts now. Content capture is opt-in and never retroactive, so traffic you did not record cannot be evaluated later.

January: build the test set and replay unchanged. Freeze a representative dataset. Run your current configuration on the new model without changing anything, so you can see what the model changed before you start changing things yourself.

February: adapt and validate. Tune prompts, parameters, tool definitions and output schemas. Score source and target on the same frozen set with the Foundry evaluation SDK: quality, latency and cost per request.

March: roll out deliberately. Move traffic in stages, keep the old deployment warm, and set the upgrade policy explicitly so nothing happens by accident. Then April is a formality instead of a deadline.

The bigger picture: models now come with a best-before date

Step back from this particular email. Microsoft states it plainly: every generally available model on Foundry ships with a retirement date, and older families are replaced over time. In the last eighteen months the recommended replacement for GPT-4o has moved from gpt-4.1 to gpt-5.1 to, now, gpt-6-luna. That is not instability. That is the rhythm of the market, and it is not going to slow down.

Which means the organisations that will do well with AI are not the ones that pick the best model. They are the ones that can change model cheaply. In practice that comes down to a few habits.

Treat model migration as servicing, not as a project. We stopped treating Windows feature updates as heroic one-off projects years ago. Model versions deserve the same routine: an owner, a calendar and a repeatable test.

Make the evaluation set a product asset. Your prompts are cheap to rewrite. Your curated set of real inputs and agreed answers is what makes every future migration fast. Feed fresh production traces back into it after every cycle.

Decouple your code from the model name. Call a deployment name, not a model version, and keep model choice in configuration. Consider whether model router fits workloads where you care more about cost per answer than about one specific model.

Put cost per answer on the dashboard. With reasoning models, cost per token tells you little. Cost per successful answer tells you whether the change was worth it.

Clean up afterwards. Migrations leave zombie deployments behind. Retiring the old one, and telling the people who wrote documentation about it, is part of the job.

The bottom line

The 14 April 2027 retirement is not a crisis. Five months is enough time, provided you use it. The risk is not that your application goes down. The risk is that it keeps running, on a different model, with different behaviour and a different bill, and nobody notices until a customer or the finance team does.

So check your upgrade policies this week, start capturing traffic this month, and decide on your own terms when you move. And while you are at it, build the habit rather than just finishing the task. There will be another one of these emails. There always is.
